> Started from a WebUI manual-test report (three "the dashboard doesn't reflect
> my config" bugs) and ended with **Maestro v1.0.0** published — public binaries
> for macOS / Linux / Windows. Along the way two release-only gaps in `release.yml`
> surfaced *at tag time* and had to be hot-fixed before the release would publish.

## Done

### Epic #127 — WebUI dashboard state accuracy (closed)

Three symptoms, all the same shape — **the data already existed, the view just
ignored it**:

- **#128 — overview "当前运行" mis-onboarding.** `/api/overview` was 100%
  dispatch-log driven. The "配置团队" CTA fired whenever `cumulative.dispatches
  === 0`, so a configured team with no dispatches yet looked unconfigured. Fix:
  endpoint now reports `team.status` (configured/absent/invalid) via a
  never-raising `_team_status()`; the panel keys onboarding to team config, not
  dispatch count, and shows a "去修复" link on invalid config.
- **#129 — scaffold didn't list applied projects.** `~/.maestro/projects.json`
  is written on every apply and `read_registry()` returns it sorted, but
  `/scaffold` only rendered the form. Fix: lists applied projects (path +
  last-opened + take_over plan link) with an empty-state placeholder.
- **version display (#1 completed).** Originally deferred; at release we made
  `version` a Jinja env global so the sidebar shows it on *every* page, not just
  the index route.

### Two release-only hotfixes (PR #131 + a notes edit)

- **Smoke-test hardcoded version.** `release.yml`'s "Smoke-test binary" step
  asserted `grep -q "maestro 0.1.0"`. The 1.0.0 binary printed `maestro 1.0.0`
  → all three OS build jobs failed → the release job (gated behind them) never
  ran → nothing published. Fix: tag-aware check — on a tag build, assert the
  binary version matches the tag (`maestro ${GITHUB_REF_NAME#v}`); on a dry-run,
  require a semver shape. Stronger than before *and* never stale. Landed on
  `main` via #131, then re-tagged `v1.0.0` at the fixed commit.
- **Release-notes template placeholder.** The Release published with the
  workflow's unfilled template (`# Maestro <tag>`, "(Edit before tagging.)",
  empty title). Fixed this release's notes via `gh release edit`; spawned a
  follow-up to make the template auto-fill so it can't recur.

## Distinctive moments

### 1. The release failed on a step nothing exercises until you tag
The version bump was correct everywhere the CI gate looks (576 tests + ruff,
all green, locally and in CI). But `release.yml`'s smoke-test and notes-template
**only run on a tag push** — so a stale hardcoded `0.1.0` and a placeholder body
sailed straight through every check and only blew up at release time. The
lesson is concrete: **a version bump's prep must touch `release.yml`**, not just
`__init__.py`/`pyproject.toml`. The new tag-aware smoke check now turns "binary
version ≠ tag" into a hard release failure, so the *next* forgotten bump is
caught by the release itself.

### 2. "Data exists, view ignores it" is a cheap, high-value bug class
Both #128 and #129 were one-API-read fixes with no new storage or model. Worth
pattern-matching for in a maturing app: the backend already records the state;
the surface just hasn't caught up.

### 3. Reviewer concerns judged, not blindly obeyed
Three of four reviewer passes were clean; the "concerns" verdicts were a
false-positive unused-import (the reviewer only saw the snippet, not the apply
route that uses it — confirmed via `ruff` + grep) and an anchored-regex
assumption that's moot for unanchored `grep -E` (verified with a prerelease
string). Documented the override rather than chasing a clean "pass" on
non-defects.

## Lessons learned (carry-forward)

1. **Version-bump prep must include `release.yml`.** The CI gate doesn't exercise
   release-only steps; grep the release workflow for the old version string when
   bumping. The smoke check is now tag-aware so this specific gap self-catches.
2. **Release-only steps need a dry-run path.** `workflow_dispatch` builds + the
   tag-aware smoke now give a way to validate the binary version assertion
   without cutting a real tag. Consider exercising it pre-release.
3. **Re-tagging an un-published release is clean.** Because the release job is
   gated behind the build jobs, the first failed run published nothing — so
   delete-and-recreate of `v1.0.0` at the fixed commit was safe and gave the
   intended version number (vs. burning a `v1.0.1`).
4. **Post-release, create the next dev branch immediately.** Did it (`v1.1`);
   this is the rule that exists specifically to stop drift-to-main.
