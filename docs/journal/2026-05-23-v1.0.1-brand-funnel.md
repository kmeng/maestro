## Distinctive moments

### 1. logo 迭代里 AI 的"专业一票"
维护者偏爱对称星芒，但它撞脸通用 "AI sparkle"。没有顺从，而是指出辨识度
风险并给出"加指挥家人格 + 打破对称"的方向；最终在维护者"中间画成 M"的指令
下收敛到「中心 M 节点 + 周围 AI 网络芒点」。审美主权在用户，专业顾虑要说出口。

### 2. 闭环规则抓出一条"反向死链"
署名链接 `/about` 原计划放 #133，但 `/about` 在 #134 才存在 → 会是死链。
把署名挪到 #134，避免"有 caller 没 interface"。闭环规则的对偶情形。

### 3. "1.0 已 tag 不可改写" → 1.0.1 补丁
维护者想把品牌"算进 1.0"。澄清约束：v1.0.0 是不可变 tag，现实做法是补丁版
v1.0.1。分支名（v1.1）不决定版本号——内容照样作为 1.0.1 发布，零返工。

### 4. funnel 的拉新 vs 留存
WebUI 是本地的，关于页只触达"已安装用户"（留存/转化）；真正拉新靠 README +
release notes（GitHub 访客）。同一个"引流"诉求，触点按受众分层才有效。

## Lessons learned（carry-forward）

1. **审美用户主权，专业顾虑要表达**：logo 这种主观物，先给独立判断再服从决定。
2. **闭环规则是双向的**：不仅"加 interface 要有 caller"，"加 caller 也不能指向
   不存在的 interface"。
3. **已发布 tag 不可变**：补全已发布版本 = 补丁版，不要试图改写历史。
4. **分支名 ≠ 版本号**：发版时再定 semver，dev 分支名不绑死版本。
5. **commit message 别用 `$(cat <<EOF)` 塞进带链式命令的一行**：heredoc 在
   子shell + `&&` 链里会 "bad substitution"。改用 `git commit -F <file>`。
6. **cheap worker 要 trust-but-verify**：coder 空返回、scribe schema 警告都
   出现过；重试 / 取 raw 字段即可恢复，不必回退到手写。
