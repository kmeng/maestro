## Distinctive moments

### 1. Two user reversals, both anchored to the same principle

**Reversal 1 (writer role scope)**: I proposed delegating ADR /
methodology / design docs to a new "writer" role. User pushed back
hard with the foundational-design principle. I had to redraw — only
the residual rendering surface (journal / BUILD_LOG /
troubleshooting) qualifies for delegation. Resolution: no new role,
extend `scribe` content_type.

**Reversal 2 (spec_writer promotion)**: I proposed promoting
`spec_writer` with "rendering-only" scope (decision sheet → spec_writer
renders → orchestrator reviews). User asked the right question:
*"如果拆分这么细，是不是让架构变得复杂？除了降低开销，是否还会增加
开销，比如 opus 二审 spec？"* I'd anchored my analysis on Opus's
direct-write cost vs spec_writer's spec output cost — **missing four
overhead items**:

| Overhead I missed | Magnitude |
| --- | --- |
| Opus must read back rendered spec for L5 review | ~$0.06/task |
| spec_writer fail-and-redispatch (20-30% per coder T10.1 base rate) | ~$0.015/task amortized |
| Opus patch overhead (~50% cases need small edit) | ~$0.04/task amortized |
| Permanent architectural tax (new role + artifact + pipeline stage + doubled L5 surface) | One-time but compounds |

After full accounting, the saving shrank from ~53% to ~27%, absolute
~$0.08/task. Withdrew the proposal. Promoted `spec_writer` would have
been a borderline-positive decision that imported permanent complexity.

Both reversals share a meta-pattern: I framed the question as
"economics" (will it save money?) when the user framed it as
"principle" (does it cross the judgment-vs-execution line?). The
principle frame is more discriminating — it can reject a proposal
that's economically positive but architecturally compromising.

### 2. The auto-mode classifier block on `#16` close

Closing a pre-existing issue I didn't author flagged the auto-mode
classifier. Reasoning cited: "user's '按你的推荐' doesn't specifically
authorize this closure" + memory `feedback_issue_close_requires_full_DoD`
about not closing without DoD. I surfaced the block and explained:
(a) user explicitly listed "关 #16" in the approved plan, (b) the
memory rule targets premature closure of active work; #16 was already
`DEFERRED` and superseded by shipped work. User authorized with `go`.

Lesson: when the classifier blocks, surface the block + explain the
specific reason for override request. Don't try alternate-tool
workarounds.

### 3. Roadmap intentionally not pre-decomposed into issues

I had to make a call between "open 15 placeholder issues attached to
v1.0 milestone" vs "keep work in roadmap, open issues at start-of-
work time". Chose the latter. Rationale: a milestone with 15 stale
issues conveys less signal than one with the actually-in-flight
issues. Roadmap doc is the scope-of-record; issue tracker is the
active-work surface; merging them creates noise.

This is now codified as a "Cadence + process" section in roadmap-v1.md.

### 4. Boundary distinction `scribe` vs `writer`

The crucial line I almost missed when first proposing the writer role:
`scribe` already does "render already-decided events into structured
markdown" (commit/PR body). The proposed writer role was the same
shape. Once I framed both as content_type variants of a single
"rendering" role, the choice between "extend scribe" vs "new role"
became obvious — extend.

The rule for role-vs-content_type: new content_type when shape +
input signal type + model + failure mode all match an existing role.
New role only when at least one of those differs meaningfully.

## Lessons learned (carry-forward)

1. **Principle frames are more discriminating than economic frames.**
   "Does this cross the judgment-vs-execution line?" rejects proposals
   that "is this economically positive?" would let through. When
   proposing architectural changes, lead with principle check, not
   savings math.

2. **Optimization proposals need 4-item overhead accounting, not
   2-item.** (a) direct new cost, (b) verification/review cost, (c)
   failure-and-redispatch amortized cost, (d) permanent architectural
   tax. Skipping (b)(c)(d) inflates apparent savings 2× routinely.

3. **Roadmap doc and issue tracker have different audiences.** Roadmap
   is for "6 months from now" readers; issues are for "currently
   writing the PR" doers. Don't pre-create placeholder issues to
   "remind" of work — the roadmap doc already does that, more
   readably.

4. **Auto-mode classifier blocks are usable signal.** When blocked,
   surface the block + explain why override is appropriate. Don't
   route around. The classifier flagged #16-close because the
   approval pattern was indirect ("按你的推荐") + the action class
   was on a pre-existing issue.

5. **`scribe` vs `writer` distinction taught me the role-vs-content_type
   rule.** New content_type when shape + input + model + failure mode
   match existing role; new role only when meaningful difference in at
   least one. Will save future role-inflation proposals.
