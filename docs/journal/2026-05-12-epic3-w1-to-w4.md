## Process learnings

- **Estimation can be 4–5× off when reading from selective sources.**
  Initial T3.5 estimate (1h, 4×80 ≈ 320 lines) was based on librarian's
  "verbatim quote" subset of `_coder_impl`. Actual files were 322 +
  301 + 223 + 122 = 968 lines. Realizing this mid-W4 → discussed split
  with user → opened 3 sub-issues. Lesson: when planning a "fanout"
  refactor, run a quick `wc -l` on each instance BEFORE estimating —
  the librarian's selective quote is not the function's full length.

- **Spec failure cost continues to dominate.** Three trips to
  `feedback_coder_spec_inline_signatures` family today:
  - T3.5 original scope referenced non-existent `maestro/server.py`
    → spec failure caught at integration (T3.2 had similar).
  - T3.5a reviewer first round fail because I abbreviated the test +
    pyproject in the reviewer's `code` payload — same as T3.5c
    later.
  - T3.5c reviewer concerns × 3 from the same abbreviation pattern.
  Net wall cost from these: ~10 min orchestrator rewrite + 1 reviewer
  re-dispatch + 1 reviewer dismiss-with-rationale (audit-trail cost).
  Memory entries `feedback_verify_paths_before_spec` +
  `feedback_worker_payload_completeness` are direct codifications.

- **Repeat-3-times memory rule continues to hold.** Both new memories
  today (`worker_payload_completeness` and `verify_paths_before_spec`)
  were triggered by the THIRD instance of the same mistake. Two
  occurrences felt like flukes; three forced the codification. Will
  hold this as the trigger threshold going forward.

- **Polling-while-user-is-AFK isn't free.** When ScheduleWakeup
  worked autonomously (sessions before today's restart), the worker
  dispatch experience felt like a fast loop. After the restart broke
  ScheduleWakeup auto-fire, the same workflow required user-side
  pings between every worker turn. User explicitly called this out
  as degraded UX. **Background-agent pattern** (`Agent run_in_background:true`
  with the job_id inline in the prompt) was discovered mid-session
  and verified working. Going forward this should be the default for
  worker polling.

- **User pushback flags my abstraction leaks early.** Three times
  today user asked sharp questions that exposed my reasoning gaps:
  - "B 的设计有什么好处，为啥我看起来更复杂呢？" → forced me to
    realize my B diagram was the migration phase, not terminal state.
    Reframed B as cheaper at end-state.
  - "是不是 T3.5 改动导致的 polling 问题？" → forced me to actually
    check `list_scheduled_tasks` (empty) rather than guess.
  - "你不是已经解决了我来触发 poll 的问题了吗？为啥还让我来触发？" →
    forced me to acknowledge I'd said-not-done; led to the
    background-agent discovery.
  Pattern: user's "why" questions are sharper than my "how" answers
  when I haven't actually verified the claim. Default to running the
  check before answering.

- **Worker payload completeness ≠ coder spec completeness.** The
  inline-signatures memory previously codified that COODER specs
  need full signatures. Today's 3rd-hit lesson is that the rule
  applies to ALL worker arguments: reviewer's `code`, scribe's `diff`,
  librarian's `document_text` — anywhere a worker uses an argument
  to ground its judgment. Comment placeholders ("# similar pattern,
  see file") save ~2k tokens up front and cost ~10k tokens + re-dispatch
  on the back end. False economy.

- **Dogfood-user UX is a distinct category from shipped-user UX.**
  Today's polling regression affects only the dogfooding workflow
  (orchestrator in Claude Code session, watching workers). Shipped
  Maestro users don't hit it because they're in their own Claude Code
  sessions polling `job_status` MCP tool directly. This means
  dogfood-UX-only regressions can ship without affecting shipped UX
  — but they slow the dogfood team's iteration, which slows the
  project itself.

- **The 3-issue split pattern works well for "underestimated fanout"
  tasks.** Instead of trying to land one mega-PR, T3.5a (foundation
  retrofit) → T3.5b (one example handler) → T3.5c (fanout to other 3)
  is a cleaner pattern: foundation lands quickly, the example sets
  the template for the fanout, the fanout is mechanical. Will keep
  this in mind for similar fanouts in Epic 3 W5 and beyond.
