### #101 — 14 个模板 + 10 个测试中文化

**决策前置**：用户问"中英可切换的代价"。我回了三段分析：
- 客户端 i18n (vanilla JS + `data-i18n` + localStorage)：~1 天主要在打标签
- 服务端 i18n (Jinja2 babel/gettext)：~2 天，引依赖 + middleware
- 静态中文化：~2h

建议先静态中文化、不做 toggle。理由：项目当前 1 个用户（自己 + 设想的国内 dev），shipping users 还没有真实的英文需求；i18n 一旦做就要长期维护两套翻译，对 v0.0.4 工具是过早投资。用户接受。

**翻译词汇表**（一次性敲定）：Overview→总览 / Team→团队 / Scaffold→脚手架 / Live→实时 / History→历史 / Savings→成本节省 / Problems→问题。加上 KPI 标签、panel 标题、table headers、JS 动态字符串、empty-state 全套。开 issue [#101](https://github.com/kmeng/maestro/issues/101) 把词汇表写进 body 锁死。

**Coder 一发 dispatch**：spec 给 14 个文件，6 个文件提供 verbatim 内容（_base / index / savings / savings_empty / savings_disabled / savings_error，因为它们改动量大），8 个文件只给 diff-style "改这一行"。Coder（deepseek-v4-pro，228s，15k tokens）老实地区别处理：6 个 verbatim 文件全文输出；8 个只改一行的诚实地说 "Full file content cannot be provided because the original full content was not supplied"，只给出 changed snippet。我用 Edit 工具补上 8 个小改动。

## Distinctive moments

1. **Coder 老实承认输入不全**。它没有为 8 个只给 diff 的文件瞎编全文，而是明确说 "cannot be provided because the original full content was not supplied" + 给出 changed snippet。这种"诚实失败"比"幻觉成功"有用得多——我用 Edit 工具 30s 内补上 8 个小改动；如果它瞎编了 8 个文件的全文，发现错误的代价会高得多。

2. **Reviewer 词汇表的严格**。我承认在 "返回首页"这一处犯了"局部最优 vs 全局一致"的错——单看那一个 button，"返回首页"读着确实更地道。但 reviewer 不评估单点 UX，它对照词汇表查 diff。这是 reviewer 该做的事——一旦把词汇表写进 spec，每一处偏离都是"作者刚才忘了自己刚才在做什么"。

3. **String-literal 测试一边脆一边好**。14 个测试在 page-h1 改完后立刻失败，全部精准定位到该改的字面量。`sed` 一行批量修复。这种"脆"是好的——它强制每次 UI 文案改动都要看见所有断言、保证文案改动不会悄悄改变契约。decouple-tests-from-implementation 这条通用原则在静态 UI 文案的语境下不适用。

4. **i18n 的"未来需求"债务**。8h 做一个 toggle，但当前 0 个英文用户 + 0 个 i18n 真实请求。"我以后可能需要"是债务，不是投资——做了就要长期维护两套翻译，每新增一个 string 都翻倍工作量。不做留出"以后真有需求时重新设计"的空间。延期 ≠ 拒绝；延期 = 把决策留到信号更强时再做。
