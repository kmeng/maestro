## Decided

- **Worker scribe-prompt enrichment is the project's standing
  pattern**, not a one-off T0.3 experiment. Three things go into
  every scribe `convention` field from now on:
  1. Librarian-extracted hard-constraint quotes verbatim (so scribe
     has legal evidence to cite, not material to invent).
  2. Measured verification facts (test counts, smoke responses,
     real ports — not generated by the scribe).
  3. Explicit anti-patterns: "no speculative attribution", "no
     generic phrases like 'sets up foundation'". Forbidden vocabulary
     is more effective than positive guidance.
  Today's data point: with the enriched prompt, worker scribe
  output was indistinguishable from orchestrator-shadow output and
  was actually **safer** in one respect (explicitly marking the
  single-source-of-truth decision as "internal — not attributed to
  any ADR", which my orchestrator shadow had only conveyed
  implicitly). The "shadow gap" is mostly a context-injection gap,
  not a model-capability gap.

- **Telemetry control = configurable path, not master toggle**.
  User initially raised the perf-toggle question. Bench-of-back-of-
  envelope: JSONL append is ~1ms per dispatch; worker walls are
  60–500s. Overhead is in the noise — three orders of magnitude
  below the dispatch itself. Privacy / test-isolation are the real
  reasons for control, and `MAESTRO_DISPATCH_LOG` (empty=disable,
  non-empty=redirect, unset=default) covers all three cases more
  flexibly than a boolean. Recorded as D6 in #56's body.

- **Three open questions (OQ1/2/3) on Epic 6 design were
  user-delegated** ("依你"). Resolutions: (a) helper script
  `scripts/begin_task.sh` rather than CLAUDE.md behavioural mandate
  — lighter, recoverable when humans run workers directly. (b) T6.6
  (README link) lands immediately after T6.3 produces the first
  rendered page, not at end of epic. (c) Renderer-determinism CI
  verification deferred to v0.0.4 follow-up. Recorded as D7/D8/D9
  in #56's body.

- **Banner format asymmetry is the right design**, not a wart to
  paper over. Coder produces plaintext (orchestrator reads code,
  not JSON); the other three produce strict JSON. Banner shape is
  identical (`[<tool> dispatch — <model> — <wall>s — <tokens>
  tokens]`); placement varies by output type (plain-prefix vs
  `_banner` field). `extract_banner()` reads either uniformly. This
  preserves both contracts cleanly rather than retrofitting one
  worker to the other's convention.

## Process learnings

- **"Wait, check the logs first" is a debugging primitive that
  the orchestrator should reach for before declaring a worker
  stuck**. Mid-T6.2 the coder dispatch had been "running" for
  ~10 minutes (well past the nominal 120s timeout), so I escalated
  to user with three remediation options including "I write the
  code myself". User said "Wait. 模型不会出问题，看下日志". Three
  shell calls later, the truth was visible: dispatch had completed
  in 383s, log_dispatch wrote the entry, but the async job
  tracker's `record.status = "done"` apparently lagged the polling
  by some interval. The fix wasn't to abandon — it was to check
  one more poll. Generalises: **before declaring a system stuck,
  check whether it's actually stuck or whether your visibility
  layer is stuck**. The two failure modes look identical from the
  outside but have completely different remediation.

- **Designing for "estimate vs measured" honesty pays compounding
  interest**. The Epic 6 design distinguishes *measured* fields
  (worker API responses captured at dispatch) from *estimated*
  fields (Opus baseline, 50/50 token splits, banner-gap-era
  backfills) in the schema (`is_estimate` + `est_method`). The
  rendered page reflects this in a column (✓ / ⚠) and a footnote
  excluding ⚠ rows from per-role averages. The discipline isn't
  ornamental — it's what lets a public claim (~56% saved on T0.2)
  age into a measured claim without retracting anything. The
  estimate-day version of the page would have aged poorly within
  weeks; the measure-from-T0.4 version doesn't have a half-life.

- **GitHub has parallel mechanisms with non-obvious overlap**.
  Title convention "T<N>.<M> [Epic <N>]:" is a *hint* readable by
  humans and by `gh issue list`. The native sub-issues API is the
  *graph relationship* readable by GitHub's own progress tracker
  and any tool walking the parent-child edges. Easy to do one and
  miss the other. Today's miss: I created Epic 6 sub-issues with
  only the textual hint; user caught that the epic's progress
  bar wasn't reflecting children's states. Diagnostic via
  GraphQL on Epic 5 confirmed the correct convention is *both*.
  Generalises: **when working with hierarchical structures in any
  collaborative system, distinguish "human-readable label" from
  "machine-readable edge" and verify both exist**. Memory file
  `feedback_epic_sub_issue_graph.md` records the rule + the
  GraphQL verification command for next time.

- **Coder dispatches on big specs are slow but trustworthy**.
  Today's two big coder calls: 383s (15114 tokens), 478s (17045
  tokens). Orders of magnitude over the small-spec wall (60–120s
  range from T0.3 / Epic 5). DeepSeek-v4-pro chews through long
  reasoning + multiple files but doesn't error out. Practical
  consequence: **for big specs, set the orchestrator's polling
  expectations in advance**. "I'll check at +90s, +5min, +10min
  in the meantime I work on X" is a real strategy; "poll every
  30s and panic at 5min" produces a worse outcome (today I
  almost did the second, and was wrong).

- **Surfacing uncertainty before acting is the orchestrator's
  highest-leverage habit**. Three moments today reinforced this:
  (1) Banner-parity AC said "prefix result_text" but JSON workers
  can't be prefixed without breaking parsers — surfaced before
  coding, design + #57 body amended, then coded. (2) Sub-issue
  graph missing — surfaced and diagnosed before the next epic
  cycle replicated the mistake. (3) Coder dispatch "stuck" —
  surfaced the dogfooding-blocker, didn't silently write the
  code myself, and the user's check-the-logs prompt found the
  truth in three commands. Each surface + pause cost seconds;
  silently choosing wrong would have cost edits-to-undo, an
  inconsistent epic structure, and a working dispatch
  abandoned. CLAUDE.md's H6 ("always surface uncertainty") is
  not a politeness norm — it's a tactical primitive with
  measurable ROI.

- **The orchestrator-as-final-integrator is non-trivial and
  worth defending**. Worker output today consistently had ~1–3
  minor API mismatches against the actual host project (coder
  guessed `_dispatch_coder_impl` instead of `_coder_impl`,
  `deepseek_client` instead of `deepseek`, `pytest-asyncio`
  instead of `asyncio.run`, JSONL `finished_at` instead of
  `wall_s`). These are exactly the mistakes someone working
  cold from a spec would make — they're not hallucinations,
  they're plausible guesses that don't match the actual codebase.
  The orchestrator catches them at integration time because the
  orchestrator has lived in the codebase for the session and
  knows the real names. **The "AI as integrator" role is worth
  ~10–20% of the diff but is what makes the other 80–90% of
  the diff (worker-generated) survive contact with the actual
  codebase**. This is a scope of work that AI alignment
  discussions often skip, but it's what makes worker dispatch
  economically viable on a real project.

- **One session, five closed loops**. Today's arc: T0.3 → Epic 6
  design → T6.1 → T6.2 → T6.3, plus the sub-issue graph fix.
  Each was a true closed loop (`main` runnable after every merge,
  tests green, issue closed with a comment). The compounding
  effect: by session end, Epic 6 is 3/7 and the load-bearing
  pieces are shipped, vs the alternative shape of "a lot of
  in-progress branches and partial PRs". The closed-loop
  discipline isn't paid back later — it's paid for during the
  session, and it leaves you cleaner at every checkpoint.
